# Issues found during the AlumStep_D ladder-swap debugging session (2026-08-22)

Raised directly by the user while reviewing live WebRTC sessions and rendered screenshots of the
15 subtasks. Recorded as reported; fix status noted where work has started.

## Ladder / platform stance

1. **Ladder too far from the wall-mounted fixture** to be reachable, when the fixture draws a
   wall mount. (Observed in the ad-hoc WebRTC inspection session, not yet traced to a specific
   constant -- the preset's own `couple_ladder_to_fixture` coupling was suspected but not
   confirmed as the cause.)
2. **Robot not standing on the ladder's top platform** -- ended up on a rung below it, or
   sideways/misaligned with the platform rectangle. Root-caused during this session to two
   compounding bugs: a guessed platform position instead of a measured one, and the robot's yaw
   matched to the fixture instead of to the ladder's own frame. **Fix in progress**
   (`subtask_tiers/balance.py`'s `stand_robot_on_ladder_top`, rewritten to use a raycast-measured
   platform offset and ladder-matched yaw; verification of the rewritten code was still running
   when this file was written).
3. **"It fits, you just placed it away from the platform"** -- user's correction after an
   inspection run showed the robot settling off the platform; confirmed the platform itself is
   large enough, the bug was in placement math, not geometry.

## Ladder asset

4. **Replace the ladder asset** with one that has a real top platform (AlumStep_D), instead of
   the original single-sided A-frame whose "top" was actually a thin, unsteppable guardrail.
   **Fix applied**: `assets.py`'s `STEP_LADDER_USD`/`STEP_LADDER_RIGID_USD`/
   `STEP_LADDER_TOP_OFFSET`, and the footprint-derived constants in `scene_cfg.py`
   (`LADDER_NEAR_RAIL_OFFSET`, `LADDER_MASS_KG`) updated. **Still open**: `TOP_ROBOT_POSITION` /
   `LADDER_WORK_PELVIS_Z` / `LADDER_READY_XY_RADIUS` (workshop-preset-derived, used by
   `Climb-v0`/`Descend-v0`'s reach-margin guards) were NOT touched -- they derive from a separate,
   older constant (`TOP_ROBOT_POSITION`) unrelated to the Replace-preset stance fixed this
   session, and need their own validation pass.

## Carry / Place (S03 / S04)

5. **Ladder rammed diagonally through the robot's torso** in both S03 (Carry Ladder) and S04
   (Place Ladder) rendered start states -- not held at the side, clipping through the chest.
   Traced to `grasp_poses.LADDER_IN_ROOT_CARRIED`, already flagged in-code as
   "UNCALIBRATED -- geometric estimate, not contact-verified." **Not yet fixed** -- real teleop
   data for this exact hold exists (Yujin's `gs://fiatlux/teleop-trajectory/ladder/dex3/...`
   recordings) but is for the Dex3 hand, while the current carry pose is paired with
   Inspire-specific joint targets; user asked to set the teleop-data fix aside for now.
6. **S03 and S04 look visually identical** in rendered screenshots. Partly by design (both
   legitimately start from a carried-ladder pose per the chain handoff), but worth re-checking
   once issue 5 is fixed, since a correct hold might make the two starts more visually distinct.

## Chain continuity

7. **General principle, confirmed correct-by-design**: each subtask should start where the
   previous one ended (e.g. S08 Carry-Bulb-to-Disposal should start where S07 Descend-with-Bulb
   ended). This is the intended chain handoff and is not itself a bug.
8. **But it's visibly not holding between S07 (Descend With Bulb) and S09 (Dispose Bulb)** per
   the rendered screenshots -- flagged by the user as a concrete case where the chain-continuity
   principle above is violated in practice. **Not yet investigated.**
9. **Ladder position should not change between subtasks where it is not being carried or
   placed** -- i.e. once S04 sets the ladder down, S05 onward should see it in the same spot,
   not a re-randomized position. Currently each subtask draws its own independent layout (by
   design, per the project's "coverage not equality" DR philosophy -- see
   `journal/specs/subtasks/00-foundation.md`), which is why the ladder visibly jumps between
   subtask renders. **Not yet resolved**: needs a decision on whether/how to share layout state
   across the balance-tier subtasks specifically, without breaking per-subtask training
   independence for the others.

## Tooling fix landed this session

- Added `FIATLUX_DEBUG_NO_RANDOMIZE=1` env var: freezes the Replace-preset layout draw to a
  fixed seed and disables all per-reset jitter for every subtask, reversibly (unset the var to
  get the original fully-randomized behavior back). Implemented in `scene_cfg.py` (`_layout_seed`
  default) and `subtask_env_cfg.py` (`SubtaskEnvCfg.__post_init__` calling
  `disable_randomization()`). This is what should be used going forward for any of the open
  items above, so screenshots/sessions are comparable across runs.
